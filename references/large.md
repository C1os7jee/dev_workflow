# 大需求编排

先读 [integration.md](integration.md)。工程方法以映射中的原版文件为准，本文件只规定调用顺序、输入输出和确认关口。

## 0. 恢复或准备

读取已有工作记录，恢复当前阶段、已确认决策、任务起点和下一步。没有记录时按集成约定创建单份需求工作记录；已经确认的阶段直接复用，不重走访谈。

执行包内 `setup-matt-pocock-skills` 的检查与必要配置。在记录中明确任务跟踪方式和领域文档位置，相关长期约定的新增按集成约定确认。

## 1. 需求澄清 → 需求确认

执行包内 `grill-with-docs`，内部映射加载 `grilling` 与 `domain-modeling`。把用户目标、规则、约束和明确不做的内容传入，沿用项目已有术语和决策记录。

将访谈收敛出的范围、规则和可观察验收条件交给用户确认，记录确认依据。没有这项确认时，不写业务实现或项目脚手架。已明确的术语和必要 ADR 按原版及项目约定保存。

## 2. 设计、规格和任务 → 方案确认

需要接口或模块设计时先读取并应用 `codebase-design`，使用访谈结果和现有调用关系形成可审阅的方案。

执行 `to-spec`：基于已确认需求及设计讨论，用原版规格模板写入工作记录的规格章节，尚未讨论清楚的重要取舍标为待确认，不新增业务假设。测试边界和实现决策进入下一次方案确认。

执行 `to-tickets`：基于规格，按原版纵向切片和阻塞关系形成有稳定编号、状态、验收条件的任务章节。原版要求的 prefactor 或迁移方案，仍须符合已确认范围和项目契约。

将方案、规格中的实现及测试决策、任务依赖和并行安排一并展示，取得方案确认后标记可实施。`to-spec` 的测试边界确认与 `to-tickets` 的提问合并在这一关；需求确认不自动批准尚未展示的方案。

## 3. 实施

顺序且集中的任务通过 `implement` 逐个推进；有明确并行收益、任务边界清楚时使用 `implement-spec` 的任务图和就绪任务调度，按集成约定处理分支、提交与工作区。

传给执行者：已确认规格、当前 ticket 编号及章节、依赖状态、可写文件范围、验证要求、集成约定位置和所需原版模块位置。子 Agent 用新上下文，不要求用户另行调用任何原版 skill。

主 Agent 处理当前关键路径，委派可同时推进的任务；写集不冲突，共用接口先由主 Agent 定下。结果返回后主 Agent 核对实际文件、集成并验证关联行为，再更新工作记录。Bug 或未知失败按需执行 `diagnosing-bugs`，不重复已完成实现。

按任务的真实依赖推进；一个切片完成且验证后才解锁依赖任务。新的关键取舍、范围变化或不可逆操作需要确认；常规实施和检查连续进行。

## 4. 集成审查与交付

任务级 `implement` 可以完成本任务审查，`implement-spec` 收尾的 `code-review` 负责完整集成变更。若完整范围已审查通过，不再调用第二次；新增集成变更或修复才重查受影响部分。

为大需求安排 `code-review` 原版的独立 Standards、Spec 审查，提供集成约定、完整实际变更范围、工作记录中的规格和项目规范。审查只读，修复由主 Agent 或有明确写集的实施者完成。

逐项核对验收与实际验证结果，记录未验证和阻碍，更新任务状态及下一步。完整结果由主 Agent 验收后交付；未经授权不提交、创建 PR 或部署。
